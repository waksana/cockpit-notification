# 待细化设计

**这些问题尚未形成实现决定。不得把下面的候选方案写成已实现能力。**
已确认的用户体验以[产品要求](requirements.md)为准。

## 1. “最终回复”的原生判定

需要首先确认固定 SDK/runtime 的事实：

- 哪些字段能区分主 Agent 最终答复与中途文字。
- `assistant.message` 的 phase 缺失、分片、重试、模型差异如何处理。
- 一次模型循环结束与一次面向用户交互结束如何区分。
- 正常结束、取消、错误、排队接续和后台工作完成的边界。
- 实时流与只含持久事件的历史补读如何得到一致结论。

不能用“最后一次看到的文本”“没有 toolRequests”“session idle”任一孤立条件
替代已证实的完整规则。必要时先做隔离原生契约实验；未知必须明确报告。

## 2. ask 的身份和历史对应

明确 requestId、toolCallId、消息身份的关系，以及同一请求更新、问答连续下一题、
原生重放和已解决请求是否仍有可定位的持久记录。

同一 ask 在提问区和历史中出现不能计算两次。已读和已回答是两件事。
“只能在实时看到、恢复后无法判定”的范围不得隐瞒。

## 3. 阅读条件

已确认需要按具体消息，而非打开即清空。待决定：

- 短消息稳定显示多久、哪些区域算实际内容。
- 长消息的阅读结束条件；不要求整条同时可见。
- 快速滚动、程序定位、折叠内容及窗口缩放的处理。
- ask 在当前提问区与历史记录中的呈现映射。
- 页面可见、前台焦点与多窗口场景；不判断用户视线。
- 键盘和辅助技术浏览时如何保持语义一致。

候选工具是生命周期受控的可见性观察和批量已读上报，不是每次滚动扫描全部 DOM。
具体阈值和 ABI 尚未确认。

## 4. 首次启用与恢复范围

需要选择首次启用时从哪里开始：启用前历史不追算，还是提供显式初始化。
不得默认把全部历史突然变成未读，也不得默默把已应统计的缺口清空。

同时确定：

- 正常重启后的增量恢复。
- 模块停用期间的新消息如何处理。
- 本体关闭期间及外部 CLI 产生的消息覆盖范围。
- cursor 失效、历史 rewind/delete、原生记录缺失时的校正。
- 对无法确认完整性的会话如何显示同步状态，而不是伪造精确数字。

持久索引、恢复检查点与事务方式属于后续工程设计，当前未选择数据库或文件格式。

## 5. 同步、计数与幂等

候选方向是模块拥有消息身份索引及单调的同步版本：

- 已读按身份提交，重复确认只生效一次。
- 计数从同一未读记录计算或事务维护，不让多个可写总数互相覆盖。
- 客户端合并短时间内的确认，明确成功、失败与待同步。
- 消息增加、删除校正和多端已读在并发下保持一致。
- 不让迟到消息/推送恢复已经清除的旧状态。

API 名称、schema、请求大小、存储保留、索引清理及离线待发送记录均待细化。

## 6. 推送投递与设备行为

需要确定：

- 前台新消息的短暂投递窗口及取消尚未发出提醒的规则。
- 每条消息的逻辑通知与系统展示卡片、重试尝试之间的关系。
- 同一账户的多设备订阅及设备过期、撤销权限、安装多个 PWA 副本的处理。
- 推送服务受理、设备展示及未知结果各自怎样表达。
- 消息已读后取消尚未发送的投递；已进入系统管道的通知怎样最终清理。
- 通知正文默认包含多少内容，以及是否只显示会话入口以减少信息暴露。

不得宣传 exactly-once 推送或后台跨设备实时撤回。VAPID 等秘密及 push subscription
不是公开配置，不得写入仓库、公开日志或前端 bootstrap。

## 7. 宿主最小配套

先核对实际需求，再决定通用接口：

- 消息/ask 呈现事实及边缘标记挂载。
- 会话数字、全站汇总和权限设置入口。
- 单一滚动所有者的可取消定位。
- 复用传输与 read-only 原生补读。
- 稳定 Service Worker 接入、生命周期和模块版本隔离。

不先造完整 UI 插件框架、第二个 Chat 或无限制调用宿主内部对象的接口。
本体配套需要独立 PR，通知业务继续留在本仓库。

## 8. 工程与交付

运行语言、存储、依赖、宿主 SDK pin、包入口、CI/Release 与分支保护需要在实现阶段落定。
可以参考 cockpit-file 的已使用流程，但不能照抄不适用的假设或复制另一工作树的依赖。

当前仓库只交付文档；下一步是逐项细化这些问题，不是默认开始编码、发布、安装或重启。
