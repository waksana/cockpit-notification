# 未读与通知：产品要求

**性质：已确认的产品方向与边界；不是实现或上线清单。**
细节尚未确认的部分统一列在[待细化设计](design-questions.md)。

## R1 · 只有一个 U

U 表示尚未确认已读的新消息条目数。每条条目显式记录自身身份与已读状态，
不是通过 session 活动时间、模型忙闲、最后一条消息时间或客户端取数 cursor 推测。

- 会话 U：该 session 未读条目的数量。
- 全站 U：各 session U 的总和。
- PWA 角标：支持时使用全站 U；不再把另一套通知数量加进去。
- 消息红线：对应同一条未读记录。
- 推送通知：关联同一条消息记录，便于它已读后清除对应通知。

“系统通知中心有几张卡片”不是第二个业务计数；操作系统的合并、隐藏和用户划除行为
不能反向改变 U 的定义。后台可以有投递尝试和设备订阅记录，但它们不是另一个未读数字。

## R2 · 计数范围

计入：

- 主 Agent 面向用户的正式最终答复。
- 面向用户的 ask 请求。

不计入：

- 思考、reasoning、增量 token。
- “我先检查一下”等中途进度说明。
- 工具调用、工具结果、后台子进程状态。
- 子 Agent 的输出。
- 用户自己的发言。
- 相同消息的重绘、重连重放或重复回调。

最终答复与 ask 的原生身份和完成边界必须核对固定 SDK 契约，不按内容关键词猜测，
也不能因为某个事件叫 `assistant.message` 或 `assistant.turn_end` 就假定一定是最终答复。
一个答复被原生拆成多个片段时的归并口径、ask 更新/重复展示的身份规则，需要在实现前细化。

目前没有确认把 plan、elicitation、错误、警告或业务目标完成另计入 U；
不能为增加提醒覆盖率而擅自扩大范围。

## R3 · 打开聊天不清空

采用逐消息阅读语义，而不是“打开会话即全读”：

- 打开聊天本身不清空 U，也不清空该会话所有推送。
- 正常向上翻阅历史，具体消息被确认已读时，逐条减少 U。
- 已加载但尚未呈现、页面在后台、仅收到 SSE/HTTP 数据，均不等于已读。
- 打开后继续到达的新消息使用同一规则，不另建“进入前/进入后”两套计数。
- 看到了最新一条，不能顺带把前面未看的全部清掉。
- “回到最新”是导航行为，不默认代替逐消息已读确认。
- 不增加独立的“全部标记已读”入口。

阅读条件需要兼顾短消息与超长回复，不要求长回复整体同时落入视口，也不把快速滚动经过
自动解释成读完。可见时长、结尾判断和辅助技术路径等仍需细化；系统只记录定义好的呈现确认，
不宣称能知道用户是否真正理解内容。

ask 已读只表示提问已呈现，**不表示已回答或可以解除原生等待**。

## R4 · 红线不改变布局

每条已加载的未读消息，在其左侧显示红色竖线；读后移除。

必须同时满足：

- 红线位于现有内容外侧可用留白，不占用 Chat 内容宽度。
- 不增加消息的 padding、margin、排版边框宽度或额外列来容纳红线。
- 不改变消息的高度、换行、横向位置或与输入框的原有对齐。
- 出现和消失不引起滚动位置、阅读锚点或布局抖动。
- 窄屏也不因标记产生新的横向滚动条。
- 红线只是状态表现，不成为一个额外的无意义焦点控件；提供相应的未读语义说明，
  不能只靠颜色让使用者理解状态。

具体采用伪元素还是其他不参与布局的标记容器属于实现方案；不得以追求标记效果为由
重写正文、依赖宿主私有 DOM 或另建滚动控制器。

尚未加载的未读条目仍计入 U；加载到原生消息后才挂接红线。不为了画标记预先加载完整历史。

## R5 · 已读、数字与通知的统一变化

每条消息的已读操作以稳定身份提交，不能仅发送“U 减一”：

- 重复确认不重复扣数。
- 多端同时确认同一条，只生效一次。
- 旧请求、旧快照不能使已经读过的条目恢复成未读。
- 一批看到的消息可批量确认，避免每个滚动事件或每条消息各发请求。
- 后端确认后的同一版状态驱动消息红线、会话 U、全站 U 和 PWA 角标。
- 对应系统通知随已读状态清理，不误清其他消息或其他会话。
- 断线、权限或存储失败需如实呈现，不能将未知状态显示为零或宣称已同步。

新消息增加和旧消息已读可以同时发生。例如原有 5 条，读了 2 条又收到 1 条，
最终 U 为 4，而不是按客户端最后一次覆盖写入得到错误结果。

模块只保存自己拥有的未读/通知信息和必要原生引用，不保存第二份完整聊天作为恢复权威。

## R6 · 每条新消息关联通知

每条符合范围的新消息有独立逻辑通知身份，通知携带足够的信息回到对应 session，
并可与该消息的已读状态关联。

若用户正在前台查看新消息，允许在投递前收到已读确认后取消尚未发送的提醒，
避免消息已显示仍反复打扰。是否设置短暂投递等待、多久、重试边界如何定义，待实现设计确认。
不把技术层投递重试解释成又多了一条新消息。

通知点击负责打开对应聊天；不能仅凭点击系统通知就假定所有回复都已阅读。
不清空其他未读消息。推送失败不删除未读记录，用户手动划掉通知也不自动标记消息已读。

## R7 · 接受异步与平台限制

网页、后端、PWA 角标和系统通知之间可以有延迟，目标是有明确版本与身份的最终一致，
不是“所有设备同一瞬间变化”。

- 在线页面应及时同步，不长期保留明知过期的数字。
- 当前设备可在可用接口范围内清理本应用自己的通知。
- 其他设备休眠、系统限制后台执行、通知已进入投递管道时，不承诺立即撤回或清除。
- API 成功受理推送，不等于设备已收到、展示，更不等于用户已读。
- 不支持角标或没有通知权限时，网页 U 与红线仍可工作；明确限制，不伪造系统已更新。
- 操作系统可能显示点、截断数字或禁止角标。网页的精确 U 不依赖这种显示结果。

## R8 · 保持模块与原生边界

未读账本、推送订阅、投递策略、设备信息和模块配置属于本模块。
原生 session、历史、队列、模型、工具和 ask 的回答生命周期仍以 Copilot 为准。

本体仅在有实际消费者时提供通用挂载、可见性、导航或资源能力。
模块不能要求本体保存未读业务副本，不能通过实验给真实 session 发消息或回答 ask。
模块活动不增加宿主 graceful 的等待条件，进程退出后的重启仍由用户或宿主设施负责。

## 验收方向

实现时至少覆盖：多会话精确求和、同消息重复事件、多端重复确认、读旧消息同时来新消息、
打开不清空、后台不误读、长回复与 ask、重连与进程重启、布局前后几何不变、
失败不伪造零值，以及浏览器不支持通知/角标时的退化。

这些是待实现验收目标，不是本仓库当前已经完成的验证。
