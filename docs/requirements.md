# 未读与通知：产品要求

**性质：已确认的产品方向与边界；不是实现或上线清单。**
具体状态转移见[状态机](state-machines.md)；尚未确认的部分统一列在[待细化设计](design-questions.md)。

## R1 · 只有一个 U

U 表示当前模块运行代内，尚未确认已读的新消息条目数。每条条目显式记录自身身份与已读状态，
不是通过 session 活动时间、模型忙闲、最后一条消息时间或客户端取数 cursor 推测。

- 会话 U：该 session 未读条目的数量。
- 全站 U：各 session U 的总和。
- PWA 角标：支持时使用全站 U；不再把另一套通知数量加进去。
- 消息红线：对应同一条未读记录。
- 推送通知：关联同一条消息记录，便于它已读后清除对应通知。

“系统通知中心有几张卡片”不是第二个业务计数；操作系统的合并、隐藏和用户划除行为
不能反向改变 U 的定义。后台可以有投递尝试和设备订阅记录，但它们不是另一个未读数字。

## R2 · 计数范围

计入：

- 主 Agent 面向用户的正式最终答复。
- 面向用户的 ask 请求。

不计入：

- 思考、reasoning、增量 token。
- “我先检查一下”等中途进度说明。
- 工具调用、工具结果、后台子进程状态。
- 子 Agent 的输出。
- 用户自己的发言。
- 相同消息的重绘、重连重放或重复回调。

最终答复与 ask 的身份按固定 SDK 和宿主控制投影核对，不按内容关键词猜测。
用户同意以显式 final 与正常主循环结束后的无 phase 答复作结构兼容判定，限制见实现说明；
不能因为孤立事件叫 `assistant.message` 或 `assistant.turn_end` 就计入。

目前没有确认把 plan、elicitation、错误、警告或业务目标完成另计入 U；
不能为增加提醒覆盖率而擅自扩大范围。

## R3 · 打开聊天不清空

采用逐消息阅读语义，而不是“打开会话即全读”：

- 打开聊天本身不清空 U，也不清空该会话所有推送。
- 正常向上翻阅历史，具体消息被确认已读时，逐条减少 U。
- 已加载但尚未呈现、页面在后台、仅收到 SSE/HTTP 数据，均不等于已读。
- 打开后继续到达的新消息使用同一规则，不另建“进入前/进入后”两套计数。
- 看到了最新一条，不能顺带把前面未看的全部清掉。
- “回到最新”是导航行为，不默认代替逐消息已读确认。
- 不增加独立的“全部标记已读”入口。

首版采用前台短回复完整可见、长回复末端可见且稳定 600ms；不要求长回复整体同时落入视口，
不把快速滚动经过自动解释成读完。系统只记录定义好的呈现确认，
不宣称能知道用户是否真正理解内容。

ask 已读只表示提问已呈现，**不表示已回答或可以解除原生等待**。
反过来，ask 已被回答/取消/替换时，撤销过期提醒，避免无法清掉的数字；
这不是声称用户已读。确认删除会话或 rewind 同样撤销受影响提醒，普通 unload/compaction 不这样处理。

## R4 · 红线不改变布局

每条已加载的未读消息，在其左侧显示红色竖线；读后移除。

必须同时满足：

- 红线位于现有内容外侧可用留白，不占用 Chat 内容宽度。
- 不增加消息的 padding、margin、排版边框宽度或额外列来容纳红线。
- 不改变消息的高度、换行、横向位置或与输入框的原有对齐。
- 出现和消失不引起滚动位置、阅读锚点或布局抖动。
- 窄屏也不因标记产生新的横向滚动条。
- 红线只是状态表现，不成为一个额外的无意义焦点控件；提供相应的未读语义说明，
  不能只靠颜色让使用者理解状态。

具体采用伪元素还是其他不参与布局的标记容器属于实现方案；不得以追求标记效果为由
重写正文、依赖宿主私有 DOM 或另建滚动控制器。

尚未加载的未读条目仍计入 U；加载到原生消息后才挂接红线。不为了画标记预先加载完整历史。

## R5 · 已读、数字与通知的统一变化

每条消息的已读操作以稳定身份提交，不能仅发送“U 减一”：

- 重复确认不重复扣数。
- 多端同时确认同一条，只生效一次。
- 旧请求、旧快照不能使已经读过的条目恢复成未读。
- 一批看到的消息可批量确认，避免每个滚动事件或每条消息各发请求。
- 后端确认后的同一版状态驱动消息红线、会话 U、全站 U 和 PWA 角标。
- 对应系统通知随已读状态清理，不误清其他消息或其他会话。
- 断线、权限或存储失败需如实呈现，不能将未知状态显示为零或宣称已同步。

新消息增加和旧消息已读可以同时发生。例如原有 5 条，读了 2 条又收到 1 条，
最终 U 为 4，而不是按客户端最后一次覆盖写入得到错误结果。

模块只保存自己拥有的未读/通知信息和必要原生引用，不保存第二份完整聊天作为恢复权威。
未读条目核销后从集合删除，但保留本运行代内的已核销身份，防止“已读先于新消息事件”
或重复事件使其复活。核销接口不通过阻塞几秒等待插入来保证正确性。

## R6 · 每条新消息关联通知

每条符合范围的新消息有独立逻辑通知身份，通知携带足够的信息回到对应 session，
并可与该消息的已读状态关联。

新消息登记后等待一个短暂窗口，届时仍未读才向有效订阅投递；
若任一客户端在此期间核销，取消尚未发送的提醒。等待用于减少打扰，不用于修补乱序。
首版窗口参数见[实现说明](implementation.md)；状态及 UNKNOWN 等投递边界见[推送状态机](state-machines.md#push)。
不把技术层投递重试解释成又多了一条新消息。

通知点击负责打开对应聊天；不能仅凭点击系统通知就假定所有回复都已阅读。
不清空其他未读消息。推送失败不删除未读记录，用户手动划掉通知也不自动标记消息已读。

## R7 · 接受异步与平台限制

网页、后端、PWA 角标和系统通知之间可以有延迟。采用完整快照和操作回执，
不要求持续广播各客户端的已读；一致性指下一次有效同步后收敛，不是后台定时保证。

- 当前页面核销成功后应用回执；打开、回前台、切会话和重连时获取完整状态。
- 其他客户端造成的已读变化可以延迟。如果本页面一直没有新同步触发，
  可以持续显示旧快照，不声称几秒内必定同步。
- 其他 session 新增未读需要可靠的模块更新告知或下一次查询；现有 session 元数据 SSE
  不足以让客户端独立重建所有 session 的未读集合。
- 当前设备可在可用接口范围内清理本应用自己的通知。
- 其他设备休眠、系统限制后台执行、通知已进入投递管道时，不承诺立即撤回或清除。
- API 成功受理推送，不等于设备已收到、展示，更不等于用户已读。
- 不支持角标或没有通知权限时，网页 U 与红线仍可工作；明确限制，不伪造系统已更新。
- 操作系统可能显示点、截断数字或禁止角标。网页的精确 U 不依赖这种显示结果。
- 由模块调用 Badging API 设置总 U，并按消息身份关闭本应用通知；两件事分别执行。
- 不为已读专门发送清除 push，不依赖静默唤醒休眠设备。清理具体通知不能仅凭一个总数，
  必须有核销身份或覆盖该消息版本的完整快照。

## R8 · 保持模块与原生边界

未读账本、推送订阅、投递策略、设备信息和模块配置属于本模块。
原生 session、历史、队列、模型、工具和 ask 的回答生命周期仍以 Copilot 为准。

本体仅在有实际消费者时提供通用挂载、可见性、导航或资源能力。
模块不能要求本体保存未读业务副本，不能通过实验给真实 session 发消息或回答 ask。
模块活动不增加宿主 graceful 的等待条件，进程退出后的重启仍由用户或宿主设施负责。

## R9 · 内存账本与重启清零

未读条目、核销凭据、计数和待发送计划不落磁盘。
每次模块重新激活建立新运行代，旧运行代账本丢弃，不从原生历史恢复未读。
不追算启用前、停机期和模块未收到的外部消息；这是明确的覆盖范围，不宣传持久 IM 未读。

客户端以新运行代的完整快照识别重置，清理旧代红线/数字与可处理的系统通知。
旧请求或迟到 push 不能恢复新代未读；休眠设备旧通知可能保留到下次获准运行。
重启清零不等于用户把旧消息读过。

推送密钥与设备订阅不属于未读账本，需要独立稳定配置来源；首版私有保存方式见实现说明。
不能因为 U 不落盘就默默让所有设备每次重启都必须重新打开才恢复推送。

## 验收方向

实现时至少覆盖：多会话精确求和、同消息重复事件、多端重复确认、读旧消息同时来新消息、
打开不清空、后台不误读、长回复与 ask、重连快照与重启清零、布局前后几何不变、
失败不伪造零值，以及浏览器不支持通知/角标时的退化。
精确的乱序输入与预期结果见[状态机时序表](state-machines.md#races)。

这些是验收要求，不能据此声称已经覆盖所有真实设备、推送平台或 provider。
源码覆盖与尚未实测的边界分别记录在实现说明和对应 PR。
