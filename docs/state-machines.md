# 未读、快照与推送状态机

**状态：设计契约，对应 0.1.0 开发源码；尚未发布或安装。** 本文把已讨论的内存账本、批量核销、按需快照、
延迟 Web Push 和 PWA 清理整理成可实施的状态契约。逻辑字段和操作名用于消除歧义，
不是已发布 HTTP/SDK ABI；已落定数值与原生兼容判定见[首版实现](implementation.md)，剩余问题见[待细化设计](design-questions.md)。
用户行为的权威说明见[产品要求](requirements.md)，宿主分工见[协作边界](integration.md)。

本文中的“必须”“不得”约束该设计；“例如”不构成固定默认值。

<a id="scope"></a>
## 1. 范围与非目标

只有一个计数 U，来自模块内存中的未读集合。模块后端决定哪些新事件成为未读条目；
客户端显示快照并报告阅读，不能从原生 SSE 独立重建全站未读集合。

本版接受以下简化：

- 一个服务实例内有一个权威模块账本；多客户端不等于多个后端副本。
  不支持把请求轮流发给彼此独立的内存实例后仍声称全局 U 一致。
- 未读、核销凭据和待发任务不落盘。模块重新启动即清空，不恢复停机前 U。
- 只统计当前运行代内能确认的新实时消息，不补算历史、停用期或停机期消息。
- 不建立消息日志重放协议、持久聊天副本、每设备已读数据库或专用未读 SSE 连接。
- 不主动广播每次已读，不发送“清除通知用的 Web Push”，不让后台页面轮询。
- 其他客户端已读带来的变化，可等本客户端下一次快照同步才生效。
- 不把 push 受理、通知显示、消息已读视作同一件事。

推送密钥、设备订阅是独立配置，不是未读账本。它们应有跨重启的稳定来源；
首版保存在模块私有 `push-config.json`，与内存账本的 generation 分开。
不能把“未读不落盘”误解为重启后必须让所有设备重新登记。

<a id="terms"></a>
## 2. 身份、版本与变量

| 符号 | 含义 |
| --- | --- |
| `G` / `generation` | 本次模块激活的不可复用身份；不是消息序号，也不是可排序时间戳 |
| `R` / `revision` | 当前 G 内的状态版本，从 0 开始，只增不减 |
| `K` / `MessageKey` | `(sessionId, kind, nativeId)`；kind 为 `reply` 或 `ask` |
| `M` | 未读 Map：K → 条目 |
| `A` | 已核销 Set：K；即使核销先于新消息到达也保留 |
| `P` | 与未读消息关联的内存通知计划及各设备发送尝试 |
| `D` | 新条目登记后到允许发 push 的等待时间；默认 3000ms，可配置 0–60000ms |
| `B` | 前端阅读确认的批量合并窗口，150ms，不等于 D |
| `createdRevision` | K 首次进入 M 的版本；重放和投递重试不改变它 |
| `subscriptionId` | 一个推送订阅的内部身份；不同设备/PWA 安装可以不同 |

`reply.nativeId` 使用原生 messageId；`ask.nativeId` 使用宿主当前 AskRequest.requestId，
与提问区及后端控制投影一致，不与 SDK toolCallId 混用。当前不为历史工具文本虚构可回答的旧 ask。

原生事件 ID 可用于事件去重，但不与 K 混用；UUID、时间戳和 provider 调用 ID 不作为通用顺序。
G 变化时，旧 G 的身份、请求及通知仍可识别，但不能写入新 G 的账本。

### 2.1 唯一计数定义

```text
U(sessionId) = M 中 sessionId 匹配的不同 K 的数量
U(total)     = M.size = 所有 U(sessionId) 的和
summary      = 只包含 U(sessionId) > 0 的会话
```

不按客户端传来的 `+1/-1` 更新账本，不把投递次数算进 U。
可以在一次原子操作中计算派生数字，不另建独立可写的总数权威。

### 2.2 不变量

1. `keys(M) ∩ A = ∅`。
2. 同一 G、同一 K 最多有一条未读记录；它进入 A 后，在该 G 内不得复活。
3. 每条未读记录最多创建一个逻辑通知计划；向多个设备投递不增加 U。
4. 所有账本变更原子完成；在变更与新版本发布之间不得 `await` 网络操作。
5. 一个完整快照的集合、会话数字、总数都来自同一 `(G, R)`。
6. 同 G 内旧版本不得覆盖新版本；不同 G 不能比较大小。
7. 只有模块权威快照或成功核销回执改变客户端的已确认未读状态。
8. push、badge、系统通知关闭的失败，均不反向修改 M 或 A。

“原子”指同一模块实例内有确定的处理先后，不要求引入数据库。异步事件处理器不得
在检查成员关系与修改 Map 之间让出执行，或必须使用等价串行控制。

<a id="inputs"></a>
## 3. 状态机输入与原生适配边界

| 逻辑输入 | 前置条件 |
| --- | --- |
| `NEW(G, K, metadata)` | 已确认属于当前 G 的新实时事件，且符合主 Agent 最终答复/ask 范围 |
| `READ(G, keys)` | 已认证客户端报告具体呈现身份；批量结构、大小和身份通过校验 |
| `RETIRE(G, keys)` | 已解决/取消的 ask、确认删除或 rewind 所影响的提醒撤销；不是用户已读 |
| `PUSH_DUE(G, K)` | 对应通知等待到期，不代表此时仍未读 |
| `SNAPSHOT` | 获取当前模块的一次完整、一致的账本投影 |
| `STOP` / `START` | 模块生命周期变化，不是某个原生 session 的 idle/unload |
| `PRESENTED(K)` | 前端满足已约定阅读条件；仅下载/挂载消息不能产生该输入 |

`NEW` 不是原始 `assistant.message` 的别名。SDK 1.0.13 中 phase 可选，
模型循环的 turn end 不一定是面向用户的最终答复。用户已确认的结构兼容判定见实现说明；
不得用关键词、孤立的空 toolRequests 或页面尾部猜补，未知显式 phase 不当成 final。

以下不得进入 `NEW`：历史分页、重连重放、启用前已有消息、来自旧模块实例的迟到回调、
进度/思考/工具/子 Agent 输出。同 G 的真实新事件重复投递仍必须由账本幂等处理。

当前实时观察不能证明覆盖宿主未收到的外部 CLI 消息；本版不为此启动历史扫描或加载所有 session。
若无法区分某一来源的新事件与重放，先报告适配缺口，不把它们全部计入。

<a id="ledger"></a>
## 4. 后端逐消息账本状态机

每个 K 只有以下三种账本状态，push 状态不在这里：

| 状态 | 内存表示 | 是否计入 U |
| --- | --- | --- |
| `ABSENT` | 不在 M，也不在 A | 否 |
| `UNREAD` | 在 M，不在 A | 是 |
| `ACKNOWLEDGED` | 不在 M，在 A | 否 |

```text
ABSENT --NEW--> UNREAD --READ--> ACKNOWLEDGED
   \----------------READ------------^

ACKNOWLEDGED --NEW/READ--> ACKNOWLEDGED
UNREAD       --重复 NEW--> UNREAD
```

### 4.1 转移表

| 当前状态 | 输入 | 下一状态 | 原子动作 |
| --- | --- | --- | --- |
| ABSENT | NEW | UNREAD | R 加一；插入 M，记 createdRevision；安排到期时间 `now + D` |
| UNREAD | NEW | UNREAD | 不改 R/U，不延后原定推送时间，不再创建计划 |
| ACKNOWLEDGED | NEW | ACKNOWLEDGED | 忽略迟到/重复的新消息，不增加 U，不推送 |
| ABSENT | READ | ACKNOWLEDGED | 记入 A；不扣不存在的未读数 |
| UNREAD | READ | ACKNOWLEDGED | 从 M 删除、记入 A、取消尚未开始发送的计划/设备任务 |
| ACKNOWLEDGED | READ | ACKNOWLEDGED | 幂等成功，无额外扣数 |
| 任意 | RETIRE | ACKNOWLEDGED | 删除受影响 M/待发计划并保留防复活凭据；不伪造阅读回执 |
| 任意 | 不同 G 的 NEW/READ | 不变 | 旧回调拒绝；旧客户端收到代际不匹配并重新获取快照 |

批量 READ 先整批校验，再对不同 K 执行转移；不允许半批成功而响应整体失败。
如果本批改变了 M 或 A，R 只加一次；完全重复的批次保持 R。
响应必须在这些变更完成后生成，不需要等通知平台完成清理。
这里 ACKNOWLEDGED 是内部的不可再入账状态：RETIRE 也复用去重凭据，
但用户语义为“过期提醒已撤销”，不能显示成“用户已经读过”。

### 4.2 为什么“删除未读”还要留下 A

```text
浏览器先呈现 K → READ 到达 → K 还不在 M → 记入 A
稍后模块 NEW(K) 到达 → 发现 K 在 A → 不加入 M
```

核销接口立即返回，不为等待新事件阻塞几秒。D 用于减少打扰，不能承担乱序正确性。

A 还阻止“先登记、后已读、又重放”的复活。最小设计在整个 G 内保留相关身份，
不保留聊天正文；不是几秒后自动删除的临时表。只有能证明不会再来迟到/重放事件，
才可以安全收缩 A。不能任意设置 TTL 后继续声称不存在复活。

M 小不代表 A 永远小；首版最多 10,000 条未读、100,000 个保留身份，超限明确失败。
不得静默逐出凭据、静默丢弃未读或返回貌似完整的截断快照。

## 5. 快照与逻辑接口

以下 schema 对应首版源码，实际路由由模块命名空间承载，不是宿主原生 API。

```text
MessageKey = { sessionId, kind: reply | ask, nativeId }
UnreadItem = { kind, nativeId, createdRevision }

FullSnapshot = {
  generation,
  revision,
  complete: true,
  total,
  sessions: [
    { sessionId, count, items: UnreadItem[] }
  ]
}
```

`sessions` 只包含非零会话，`count == items.length`，`total == sum(count)`。
数组排列不提供原生历史顺序保证，不据此实现“首条未读”导航。
同一响应不能一边读 Map 一边 await，导致 total 和 items 来自不同版本。

| 逻辑操作 | 输入 | 成功输出 | 错误边界 |
| --- | --- | --- | --- |
| `GET /state` | 无需客户端计算计数 | FullSnapshot | 未就绪/停止/响应超限明确失败，不返回空集合代替失败 |
| `POST /read` | `{ generation, keys: MessageKey[] }` | `{ acknowledged: MessageKey[], state: FullSnapshot }` | G 不符整批拒绝；无合法身份的输入明确拒绝 |

读取与核销响应均不得被 HTTP 缓存当成当前权威状态复用，使用 no-store 语义。
失败不返回 `complete: true` 的空状态；客户端必须能区分代际不匹配、输入错误、不可用和超限。

这两个操作是完整快照版的最小需求。调用端可从 FullSnapshot 直接取得非零 session 列表和
当前 session 的未读 ID，无需首屏再逐会话请求。单独 summary/session GET 可在确有需要时添加，
但不能用只含计数的响应清理具体通知。

`acknowledged` 是本批已成功记录核销的身份，包括原先 ABSENT 的身份；不是“删除了几条”。
重复 POST 安全。网络超时属于客户端尚不知道是否核销成功，可按相同 G、相同 keys 重试，
不执行补偿性 U 加一。若 full snapshot 超限，必须在提交核销前拒绝，或另有明确的成功回执协议；
本最小接口不得出现“已提交却因拼接快照报整批失败”的隐含语义。

两类客户端版本不能混淆：

- 完整快照 `(G,R)` 能决定具体集合。
- push 的 `(G,R,total)` 只提供某一时点数字，不能证明具体 K 已读，也不能冒充 FullSnapshot。

<a id="client"></a>
## 6. 网页快照状态机

### 6.1 页面状态

| 状态 | 含义 |
| --- | --- |
| `EMPTY` | 尚未拿到任何完整快照，显示未同步，不伪造 U=0 |
| `READY(S)` | 持有已接受完整快照 S |
| `REFRESHING(S?)` | 正在读取；已有 S 可以继续展示 |
| `STALE(S?, error)` | 读取失败，保留已有 S 并明确未同步 |
| `SUSPENDED(S?)` | 页面后台，不轮询；恢复前台时刷新 |
| `STOPPED` | 模块关闭，取消本模块观察/请求/计时，不能继续发布旧结果 |

```text
首次进入 / 回前台 / 切换会话 / 网络恢复 / SSE 重连
                         ↓
                    REFRESHING
                    ↙        ↘
           接受完整快照        失败
                READY       STALE
```

核销成功返回的 FullSnapshot 同样进入接受流程，不紧接着再 GET。
多个刷新触发合并为一个在途 GET；在途期间又出现较新的触发则记 dirty，
完成后必要时再读一次。不得为每条 token、每次滚动或每个非零会话分别 GET。

### 6.2 接受规则

1. 响应必须来自当前模块实例绑定的有效请求，完整性及计数不变量通过校验。
2. 同 G：只接受 `R >= 当前快照 R`。相同 R 必须有相同内容，否则报协议错误。
3. 不同 G：只能通过当前有效的全量同步重新建立绑定，不能让 push 或旧 READ 响应切换 G。
4. 重连、代际不匹配或废弃同步操作时，递增本地请求 fence 并取消旧请求；
   即使旧请求后来成功，也不能覆盖新绑定。
5. 初始没有 G 时，暂不向后端发送无代际 READ；建立快照后对仍有效的呈现重新确认。
6. 已核销身份的成功回执即使附带快照比已接受版本旧，也不能撤销其成功事实；
   清理对应在途确认，但不应用旧快照。新快照不得让这些身份在同 G 复活。

“内容相同”按身份集合、条目字段和计数比较，不要求两个等价数组的排列或 JSON 字节相同。
G 没有可排序性；不能以 UUID 大小或“最后到达的响应”判断哪个模块实例更新。
前端可以有请求 fence、待确认集合等控制状态，但没有第二份独立永久计数。

### 6.3 页面转移的补充规则

| 当前状态 | 输入 | 下一状态 / 动作 |
| --- | --- | --- |
| EMPTY/READY/STALE | 有效刷新触发，页面可见 | REFRESHING；已有 S 保留 |
| REFRESHING | 同源新触发 | 保持 REFRESHING，置 dirty；不并发再开一个 GET |
| REFRESHING | 可接受的完整响应 | READY(S')；若 dirty 未被该版本覆盖，合并再刷新 |
| REFRESHING | 网络/协议失败 | STALE；保留旧 S，下一次显式触发可重试 |
| 任意活跃状态 | 页面隐藏 | SUSPENDED；取消在途 GET，停止产生新呈现和后台查询 |
| SUSPENDED | 已在途 READ 成功 | 接受同 G 回执到缓存，仍是 SUSPENDED，不开启轮询 |
| SUSPENDED | 页面回前台 | REFRESHING；重取完整快照 |
| 任意非 STOPPED | 有效同 G 核销回执 | 缓存按版本规则更新；不改变前后台状态，不无条件另开 GET |
| 任意 | 模块停止 | STOPPED；释放作用域，旧回调不重新激活 |

请求 fence 用于废弃的 GET/实例绑定，不以“当前切到了另一个 session”为由否认
同 G 下已成功完成的旧 session 核销。READ 的成功事实按 G/K 归属，不归属当前路由。

### 6.4 哪些变化触发刷新

已确认的按需触发：初次打开、回前台、切会话、网络/SSE 恢复、自己的核销回执。
收到 push 时可通知正在使用的页面合并刷新，但不让 push 总数直接替换网页完整集合。

为“其他 session 新消息到达，当前网页数字也应更新”提供告知：
配套本体既有 SSE 承载一个**模块完成插入后的通用状态变化提示**。
`module/invalidated` 只携带 moduleId，前台据此合并读取完整快照；
G/R 由快照提供，提示不携带聊天正文、不新增 SSE 连接。

该提示属于配套宿主新增接口，不能假定旧宿主已支持。
触发必须发生在 NEW 原子写入之后，不能先看到 session 活动变化就假定模块已经登记。
本最小方案不要求为每次 READ 广播提示；别的客户端核销可以等下一次上述触发再反映。

如果不实现新增提示，则其他会话新增数字也只能等下一次查询。不得声称现有全局 SSE
足以让前端自行构造所有 session 的未读条目：当前聊天正文流只服务当前可见会话，
全局 SSE 主要是状态元数据。

没有任何新触发时，持续开着的另一个客户端可以一直停留在旧快照，不承诺“几秒内必定同步”。
这里的最终一致是**下一次成功同步后收敛**，不是后台定时保证。

<a id="read-client"></a>
## 7. 前端逐消息阅读与批量核销状态机

| 本地状态 | 输入 | 动作 |
| --- | --- | --- |
| `NOT_PENDING` | PRESENTED(K)，已有有效 G | 加入 `QUEUED(G,K)`；不先 GET 是否未读 |
| `QUEUED` | 相同 PRESENTED | 去重，不增加请求 |
| `QUEUED` | B 到期且页面/连接允许提交 | 与同 G 其他身份一起发送，进入 `IN_FLIGHT` |
| `IN_FLIGHT` | 成功回执确认 K | 移出在途集合；应用回执快照、清理对应通知 |
| `IN_FLIGHT` | 网络结果未知 | 保留待确认身份，标明待同步；相同请求可重试 |
| `QUEUED/IN_FLIGHT` | 有效完整快照已确认 K 不再未读 | 可更新显示，但若 READ 还未成功，不能因此丢掉早到核销凭据的提交 |
| 任意待确认 | G 变化 | 废弃旧 G 请求，不直接改成新 G 重发；新呈现按新 G 重新确认 |
| 任意 | 页面隐藏/消息卸载 | 停止产生新的 PRESENTED；已经确认的呈现可以保留为待提交事实 |

重要区别：快照中“没有 K”可能表示它尚未被后端登记，**不证明早到 READ 已经记入 A**。
所以 READ 在途/失败时，不能仅因一次空快照就把确认任务扔掉。

前端不需要知道全站计数规则才能报告自己真实呈现的消息身份；由模块后端决定哪些 NEW 符合范围。
历史重绘不默认产生新未读。通常只观察快照中未读的已加载消息，以及当前实时新消息的有效呈现，
不为所有旧历史堆积核销凭据。

在后端确认之前，网页保留最近已确认快照的红线/数字，可以显示轻量待同步状态；
不自行减数后再用失败补偿加回。确认之后，一次更新同一视图内的红线、会话数字和全站总数。
也不把“点通知”“点回到最新”“打开 session”直接转换成整会话 READ。

<a id="push"></a>
## 8. 后端延迟推送状态机

### 8.1 逻辑通知计划

| 状态 | 输入 / 条件 | 下一状态与动作 |
| --- | --- | --- |
| 无计划 | NEW 首次登记 | `WAITING`；记录 `dueAt = 登记时间 + D`，同 K 不重复安排 |
| WAITING | READ / STOP | `CANCELLED`，不再开始新的设备发送 |
| WAITING | PUSH_DUE 且 G 相符、K 仍在 M、有效订阅非空 | `DISPATCHED`，选取此时有效的订阅，为每个订阅建立一次发送任务 |
| WAITING | PUSH_DUE 但 G 已变或 K 不在 M | CANCELLED；迟到计时器不得复活消息 |
| WAITING | PUSH_DUE 且 G 相符、K 仍在 M、有效订阅为空 | `NO_TARGETS`；U 保留，不因后来某设备注册就补发历史提醒 |

D 从首次登记开始，不因重复事件或一次 GET 延长。前台快速核销可取消尚未发送的提醒，
不需要额外维护“哪个设备在线所以算已读”的规则。

### 8.2 每设备发送任务

一个任务由 `(G,K,subscriptionId)` 唯一标识。以下“受理”只指 push 服务响应。

| 状态 | 输入 / 条件 | 下一状态与动作 |
| --- | --- | --- |
| `READY` | 即将发送且 K 仍在 M、订阅仍有效、G 仍匹配 | `SENDING`；取得当前一致总 U/R，构造 payload 后开始一次网络发送 |
| READY | READ / STOP / 订阅失效 | CANCELLED，不发送 |
| SENDING | push 服务明确成功受理 | `ACCEPTED`；不修改 U，不声称已展示 |
| SENDING | 明确拒绝 | `FAILED`；保留 U，报告投递错误；明确失效的订阅可撤销 |
| SENDING | 超时/断开，不能确定是否受理 | `UNKNOWN`；保留 U，不伪造失败或成功 |
| SENDING | READ | 保持 SENDING；K 从账本核销，该发送可能无法撤回，后续结果只能更新投递状态 |
| ACCEPTED/FAILED/UNKNOWN/CANCELLED | 重复 NEW、旧回调 | 不再创建同一任务，不把 K 加回 M |

STOP 时等待任务取消、SENDING 请求尽力中止，随后其内存对象随 G 释放；
已发出请求是否被平台受理可能未知，不能报告为“已经撤回”。释放后的回调只丢弃结果，
不写入新的模块实例。终态不因重复计时器或重复完成回调再次发送。

最小设计不自动重试 UNKNOWN，也不通过无限重试确保送达。
明确拒绝后的重试、退避和 provider 分类若要加入，必须另行定义，不能默认存在。
这不是 exactly-once 系统通知保证：网络/平台仍可能重复投递，设备按逻辑身份处理，
所有同 K 的系统通知都应能在核销时被识别。

### 8.3 payload

```text
{
  moduleId,
  generation,
  key: MessageKey,
  createdRevision,
  revision,
  total,
  title,
  body,
  navigationTarget
}
```

`revision/total` 来自开始该次发送时的一致状态，不是登记时旧值。
`createdRevision` 用来判断某份快照是否已经覆盖这条通知；不能只靠总数或发送时间清理。
通知采用“会话有新回复”或“有问题需要回答”等固定通用文案，不包含整段聊天。
导航目标由模块构造并限制到合法宿主入口，不能信任任意外部跳转 URL。

PWA 收到 push 不需要获取完整聊天，不需要后台维持 session SSE。
它只处理本次通知、总数及少量版本/去重元数据；OS 保存实际通知，不由模块重建通知中心。
正常同 G push 不额外 GET 完整状态。未知/不同 G 时，先通过宿主 bootstrap 确认当前模块，
再取完整快照建立绑定；不为每次 READ 另发 push 唤醒休眠设备。

<a id="pwa"></a>
## 9. PWA 角标与通知清理状态机

### 9.1 统一应用动作

前台拿到有效完整快照后，执行同一逻辑 `APPLY_STATE(S)`：

1. 更新本页面未读集合与对应红线、会话 U、全站 U。
2. 将总 U 提交给支持的 Badging API。
3. 查询本应用通知，按下面的覆盖条件清理已核销通知。

三步不属于跨 OS 事务。第 2/3 步失败不能撤销后端 READ 或伪造网页未读；
记录为设备呈现尚未收敛，下一次获准运行时重试。
网页和 Service Worker 的实际角标/通知操作必须有单一串行协调路径，
避免较慢的旧 `setAppBadge` 在较新操作之后完成。
这只是本设备的执行协调，不是新的服务器计数或额外网络同步服务。

### 9.2 角标

| 输入 | 处理 |
| --- | --- |
| 有效完整快照 S | 采用 S.total；同 G 不让较旧版本覆盖设备已应用的较新数字 |
| 同 G 的新 push 数字版本 | 采用 payload.total；不执行本地 U 加一，不据此修改网页具体未读集合 |
| 同 G 的旧 push | 不覆盖较新角标；旧版本不代表它关联的消息必然已读 |
| 不同/未知 G 的 push | 不直接切换已绑定实例；需要完整同步确认，无法确认时保留已知状态 |
| total > 0 | 若支持，调用 `navigator.setAppBadge(total)` |
| total == 0 | 若支持，调用 `clearAppBadge()` 或 `setAppBadge(0)` |
| 不支持、权限/平台拒绝 | 网页状态继续有效，明确能力限制，不宣称 OS 已更新 |

有效后台通知是用户可见事件；不是通过 badge 更新绕过 Web Push 的可见通知要求。
推送带来的数字可能比网页当前完整快照新：此时只触发页面刷新，不把一个总数伪装成完整集合。
前台成功同步并完成设备应用后，再以同一快照收敛。

为了跨页面和多次 worker 执行拒绝旧更新，设备需要共享少量实例/版本与待应用记录，
不能只依赖某次 worker 内存全局变量。首版用 IndexedDB 保存 G/R/total 和最多 64 个已退役 G，
worker 串行应用变更；不保存全部聊天或完整长期未读账本。

### 9.3 具体通知清理

通知 `data` 至少保存 moduleId、G、K 和 createdRevision。
通过当前有效 Service Worker 注册的 `getNotifications()` 获取本应用通知，
筛选后调用每个匹配 Notification 的 `close()`；所有同 K 的重复展示都匹配。

| 证据 | 可以清理哪些通知 |
| --- | --- |
| 成功 READ 回执确认 `(G,K)` | 同模块、同 G、同 K |
| 完整快照 `(G,R)` 中没有 K | 仅限通知同 G 且 `createdRevision <= R` 的 K |
| 完整同步确认从旧 G 切换为新 G | 当前应用中确认为旧 G 的本模块通知；旧代被遗忘，不称为用户读过 |
| 只有 total 或某 session count | 不能据此选择具体通知 |
| 请求失败、截断快照、来源/版本不明 | 不据此清理 |

跨代清理不能简单写成“所有 G 不同的通知都删掉”，因为它也可能是快照产生后才到达的新一代：
可先枚举并固定本机通知集合 N0，再发一次 no-store 的完整 GET；在本设计的单活后端前提下，
该有效响应能判定 N0 中不属于当前 G 的本模块通知为旧代。只清理这次枚举的对象，
不顺带处理 GET 期间新来的通知。若应用绑定/请求 fence 已变，该判定作废，重新同步。
已经通过有效同步确认为过去的 generation 可作为清理证据；陌生 push 不能自行提供这种证据。

不能直接用 `U == 0` 清理枚举到的一切：快照生成后可能已经来了新通知。
也不能因 push 的 revision 旧就删除那条通知，它可能仍然未读。
归零不影响其他模块或应用的通知。

角标清零不会自动清通知；通知被划掉不会修改 U。两件事由模块明确调用浏览器接口完成。
系统通知点击只导航，阅读确认仍走 PRESENTED/READ；单独的 `notificationclose` 不生成 READ。

### 9.4 后台与平台边界

- 原生 Web Push 或兼容的浏览器机制负责后台接收与显示，不要求页面常驻。
- 不给每次 READ 发清除 push，不依赖 iOS 静默唤醒另一设备。
- Safari 的 tag 不能作为唯一去重/替换/筛选依据；使用通知 data 的逻辑身份。
- 已知已读的 push 仍可能迟到。不得把它重新加入 U；OS 通知按可用执行机会清理，
  可能保留到下一次前台快照/核销回执应用。同代普通 push 不额外 GET 来立即清理；
  不能假定所有平台都允许无提示丢弃 push 而不影响订阅。
- 旧 push 的用户可见处理必须遵守所选平台的规则；Declarative Web Push 有可见 fallback，
  也不是静默同步能力。具体支持矩阵在实现时验证，不承诺无通知闪现或即时撤回。
- 另一个休眠设备可能长期保留旧角标/通知，直到下一次成功同步或其他合法执行机会。

<a id="restart"></a>
## 10. 内存生命周期与重启

```text
STOP(G1)
  → 禁止新任务
  → 撤销观察器、等待计时器与本模块拥有的网络请求
  → M/A/P 随实例结束丢弃
  → 不等待推送平台，不增加宿主 graceful 条件

START
  → 新 G2，R=0，M/A/P 为空
  → 只接纳 G2 内可确认的新实时事件
  → 客户端完整同步后发现重置并清理旧代呈现
```

同一个原生 session 的 idle、unload/reload 不单独重置 G 或 M。
内存账本重启清空是明确的产品取舍，不是存储故障被解释成“已读全部”。
待发送请求不能跨代复制；迟到的 G1 回调不能增加 G2 的 U。

推送订阅/密钥的稳定来源独立于 G；若订阅丢失，设备未重新注册前不能接收新 push。
取消本地网络请求不证明平台没有受理 SENDING 中的 push；
旧代通知并不会随服务器进程退出而被 OS 自动移除。

<a id="races"></a>
## 11. 必须满足的时序例子

| 场景 | 输入顺序 | 必须结果 |
| --- | --- | --- |
| 正常未读 | NEW K → D 到期 | U 加一；向有效订阅发送同 K 通知，总数取发送时值 |
| 前台快速阅读 | NEW K → READ K → D 到期 | K 不在 M、在 A；U 不含 K，不开始 push |
| 已读先到 | READ K → NEW K | K 始终不进入 M；无 push |
| 重复消息 | NEW K → NEW K | 只计一次，dueAt 不变 |
| 读后重放 | NEW K → READ K → NEW K | 不复活 |
| 多客户端读同一条 | A 端 READ K 与 B 端 READ K | 只核销一次，两端重复提交都安全 |
| 读旧来新 | M={A,B}；READ A 与 NEW C 交错 | 最终 M={B,C}，U=2 |
| 回复结束前已显示 | PRESENTED K → READ K → 最终分类产生 NEW K | A 提前保护，不因较晚分类产生假未读 |
| 核销请求结果未知 | READ 已生效但响应丢失 → 相同请求重试 | U 不再减少；回执确认同一事实 |
| push 已在发送 | SENDING K → READ K → 平台受理 | U 不含 K；允许通知迟到，不能恢复未读 |
| 快照与新通知交错 | 获取 R=10 快照 → K 在 R=11 登记并通知 → 应用 R=10 | 不清 createdRevision=11 的通知 |
| 旧 push | 设备已应用 R=20 → 收到 R=18 的 total | 不倒退角标，不因旧版本直接认定 K 已读 |
| 跨代迟到 | G1 READ 在途 → 服务 G2 → G1 响应/回调 | 不写入 G2；完整同步后重新建立页面状态 |
| 跨代通知竞态 | 固定通知集合 N0 → GET 得到 G2 → 又收到 G3 通知 | G2 可用于 N0 的旧代清理，不能清同期新到的 G3 通知；G3 需再次确认 |
| 另端核销、此端不操作 | B 核销 → A 无刷新触发 | A 可以暂时保留旧状态；下次成功快照收敛 |
| 查询失败 | 当前有 U=3 → GET 失败 | 保留上次数字并标明未同步，不能显示 U=0 |
| 只划掉通知 | OS 通知关闭，没有 READ | M 和 U 不变 |

这些例子是文档验收契约，不自行证明运行结果。实际开发使用合成 runner，
覆盖身份、原子性、乱序与 UI 几何，不用真实会话、推送订阅或生产服务作实验。
